High-Performance KV Store Load Test Experiment

This project implements a multi-threaded Key-Value store server backed by MySQL and an in-memory FIFO cache. It includes a closed-loop load generator to stress test the system and scripts to analyze performance bottlenecks (CPU vs. Disk I/O).

1. Directory Structure

Ensure your project directory looks like this:

/project_root
├── CMakeLists.txt          # Build configuration
├── server.cpp              # Server source code (MySQL + Cache)
├── client.cpp              # Load Generator source code
├── analysis.sh             # Performance monitoring script (mpstat/iostat)
├── plot.py       # Python script to generate graphs
├── results/                # Folder for CSV results
├── report.pdf                # My Project Report
├── presentation.pdf            # My Project Presentation


2. Prerequisites

The project will need the following dependencies installed on Linux machine:

# C++ Build tools and CMake
sudo apt update
sudo apt install build-essential cmake

# MySQL Connector for C++
sudo apt install libmysqlcppconn-dev

# System Monitoring tools (for monitor.sh)
sudo apt install sysstat

# Python libraries (for plotting)
sudo apt install python3-pip
pip3 install pandas matplotlib


3. Database Setup

Before running the server, you must set up the MySQL database to match the credentials in server.cpp.

Log in to MySQL:

sudo mysql -u root -p


Run the following SQL commands:

-- Create Database
CREATE DATABASE kv_db;

-- Create User 'ashu' with password 'ProjectPass@123'
CREATE USER 'ashu'@'localhost' IDENTIFIED BY 'ProjectPass@123';
GRANT ALL PRIVILEGES ON kv_db.* TO 'ashu'@'localhost';
FLUSH PRIVILEGES;

-- Create Table
USE kv_db;
CREATE TABLE kv_store (
    id_key VARCHAR(255) PRIMARY KEY,
    id_value TEXT
);


4. Building the Project

We use cmake to compile the executables.

# 1. Create a build directory
mkdir build
cd build

# 2. Generate Makefiles
cmake ..

# 3. Compile
make


This will create two executables in the build/ directory:

server

client

5. Running the Experiment (With Core Isolation)

To identify bottlenecks correctly, we must isolate the Server, Database, and Client on different CPU cores using taskset.

Assumption: Your machine has at least 4 cores (0-3).

Step A: Pin MySQL (Optional but recommended)

Find the MySQL process ID and pin it to Core 0.

pgrep mysqld
# Assuming PID is 1234
sudo taskset -cp 0 1234


Step B: Run the Server

Pin the Server to Core 1. Run this in a dedicated terminal.

cd build
taskset -c 1 ./server


Step C: Start Monitoring (Bottleneck Detection)

Open a new terminal. Run the monitor script located in the root directory. This tracks CPU and Disk usage.

# Run for 60 seconds (or match your test duration)
./monitor.sh 60


Step D: Run the Load Generator (Client)

Pin the Client to Cores 2 and 3 to ensure it generates enough load to saturate the server. Run this in a third terminal.

cd build
taskset -c 2,3 ./client


Select Option 2 (Load Test Mode).

Choose your workload:

Put All (1): To test Disk I/O Bottleneck.

Get Popular (3): To test CPU Bottleneck.

Enter Threads (e.g., 8) and Duration (e.g., 60 seconds).

Identifying Bottlenecks

Check the logs in perf_logs/ generated by monitor.sh:

CPU Bound: High %usr in mpstat.txt, low Disk I/O.

Disk Bound: High %iowait in mpstat.txt or high %util in iostat.txt.
